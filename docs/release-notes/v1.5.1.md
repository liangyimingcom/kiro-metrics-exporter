# Kiro Metrics Exporter 1.5.1 升级说明

> 对比版本：1.5.0 → 1.5.1  
> 状态：内部测试中。安装包在 `release/1.5.1` 分支，尚未合并到 main  
> 安装包：仓库根目录 `kiro-metrics-exporter-1.5.1.vsix`（打包于 2026-10-14）  
> 最后更新：2026-10-21  
> 1.5.1 后续如有新的修改，会补充到本文并重新打包

## 概要

1.5.1 修复了两个统计问题，只改动了统计代码 `src/extractor.ts`：

1. Spec 模式下子 agent 写的代码，1.5.0 完全没有统计。常见表现是"执行次数正常，新建行数为 0"。
2. 用 `fs_write` / `fs_append` 修改已有文件时，1.5.0 把整个文件算成新建，数字偏高。

使用 Spec 模式的用户建议升级。

## 修复内容

### 1. Spec 模式子 agent 写的代码不再漏算（12ce28a）

**现象**：在 Spec 模式里执行任务，Kiro 界面显示文件已成功创建或修改，但插件统计的当天新建行数为 0 或明显偏低，执行次数正常。

**原因**：Spec 模式下，主 agent 会把任务交给子 agent 执行。Kiro 把两边的记录分开保存：

```text
~\.kiro\sessions\<工作区>\sess_xxx\
├── messages.jsonl        主对话：用户消息、主 agent 自己的操作
└── sub-executions\
    └── <UUID>.jsonl      子 agent 的操作
```

1.5.0 只读取名为 `messages.jsonl` 的文件，`sub-executions` 下的文件被跳过，子 agent 写的代码全部漏算。执行次数来自主对话，所以照常统计。

**修复**：同时读取 `sub-executions\*.jsonl`。子 agent 的记录不会增加执行次数。

### 2. 修改已有文件的 fs_write / fs_append 按差异计行（ea7d516）

**现象**：较新版本的 Kiro 中，`fs_write` 也可以直接修改已有文件。这类记录带的是修改前后的完整文件内容（`originalContent` / `modifiedContent`），而不是只有 `text`。

**原因**：1.5.0 把这类记录当成新建文件，按修改后整个文件的行数计入"新建行数"。修改后的内容为空（清空文件）时，整条记录被丢弃。

**修复**：带有 `originalContent` 的 `fs_write` / `fs_append`，按修改前后的逐行差异计入"修改+行"和"修改−行"，算法与 `str_replace` 相同。只带 `text` 的调用（新建文件）和 `str_replace` 的计法不变。

| 操作 | 1.5.0 | 1.5.1 |
|---|---|---|
| 100 行的文件改 1 行 | 新建 100 | +1 / −1 |
| 清空一个 100 行的文件 | 不计入 | −100 |
| 用 fs_append 在 100 行的文件末尾追加 2 行 | 新建 102 | +2 |

## 升级后数字会怎么变

`Chat_AICodeLines`（净增行数）= 新建 + 修改+ − 修改−。

| 使用场景 | 新建行数 | 修改+ / 修改− | Chat_AICodeLines |
|---|---|---|---|
| Spec 模式，子 agent 写代码 | 增加（从 0 或偏低恢复） | 增加 | 增加 |
| 用 fs_write 修改已有文件 | 减少（不再按整个文件算） | 增加 | 通常明显减少 |
| 其他情况 | 不变 | 不变 | 不变 |

执行次数（`Chat_MessagesSent`）的计法不变。

## 升级步骤

1. 获取安装包：仓库 `release/1.5.1` 分支根目录下的 `kiro-metrics-exporter-1.5.1.vsix`。合并到 main 后，在 main 分支根目录。
2. 安装：在 Kiro 扩展视图右上角的 `...` 菜单中选择"从 VSIX 安装..."（Install from VSIX...），选中安装包。原有配置会保留。
3. 重新加载所有 Kiro 窗口：在命令面板执行 `Developer: Reload Window`（中文界面为"开发人员: 重新加载窗口"），或完全退出 Kiro 后重新打开。没有重新加载的窗口仍在运行 1.5.0，它的自动上传会把数据覆盖回旧值。同一个人在多台电脑上使用 Kiro 时，每台都要升级。
4. 确认版本：Metrics Exporter 面板顶部显示 `Kiro Metrics Exporter v1.5.1`。
5. 按《子执行统计修复说明》给 1.5.0 打过本地补丁的用户，升级后不需要再运行补丁脚本。

**回滚**：用同样的方法安装仓库中的 `kiro-metrics-exporter-1.5.0.vsix`，再重新加载所有窗口。之后的上传会按 1.5.0 的算法覆盖数据。

## 历史数据

插件上传到 S3 的文件按"用户 + 日期"命名（`.../yyyy/MM/dd/00/kiro-ide-{userId}.csv`），同一天只有一个文件，重新上传会直接覆盖。升级后，旧日期要重新上传，S3 上的数字才会变成 1.5.1 的结果：

| 要更新的日期 | 做法 |
|---|---|
| 今天 | 点 Upload Today |
| 最近 7 天（不含今天） | 重新加载窗口后，自动上传会重传这 7 天；也可以手动点 Upload Last 7 Days |
| 更早的日期 | 点 Upload All Till Yesterday。它会按 1.5.1 重算全部历史并覆盖，其他日期的数字也可能变化 |

注意：

- 插件根据本机的 Kiro 会话记录重新计算。会话记录被删除或换了电脑后，无法重算。
- 同一个人在多台电脑上上传时，同一天的文件会互相覆盖，以最后一次上传为准。1.5.0 也是如此。
- S3 上的文件被覆盖后，数据库中已有的记录是否跟着更新，取决于从 S3 入库的程序，目前尚未确认。已发现一条记录入库后从未更新过（`created_at` 与 `updated_at` 相同），说明很可能不会更新。确认之前，内部测试请以插件 Output 面板中的统计报告或 S3 上的文件为准，不要以数据库或看板为准。

## 验证情况

| 验证方式 | 结果 |
|---|---|
| 构造的会话记录，覆盖上面两项修复和失败的写入 | 结果符合预期。只带 `text` 的 fs_write 和 str_replace 与 1.5.0 结果相同，失败的写入不计入 |
| 一台 Kiro 1.0.138 电脑的真实数据（148 天） | 1.5.0 与 1.5.1 结果完全一致，这台电脑的数据没有触发这两种情况。当天新建和修改的行数与手工计算一致 |
| 一位 Spec 模式用户，使用与 12ce28a 等效的本地补丁 | 某天从全部为 0 变为新建 1,644、修改 +188 / −50 |

尚未验证：Kiro 1.2 及以上版本的真实数据。第 2 项修复只在构造的会话记录上验证过。

## 已知问题

1. **同一轮对话的多份记录只保留一份。** 子 agent 的记录与主对话那一轮使用同一个 executionId（目前看到的记录都是如此）。同一轮里主 agent 和子 agent 都写了代码，或者派了多个子 agent 时，插件只保留改动量（新建 + 修改+ + 修改−）最大的那一份，其余不计入。因此这类日期的数字仍可能偏低，个别情况下新建行数和净增行数甚至会比 1.5.0 低。例如主 agent 新建了文件，子 agent 只修改了代码但改动量更大，这一轮的新建行数会变成 0。

   构造样例：同一轮里主 agent 修改 tasks.md（+1 / −1），两个子 agent 分别新建 3 行和 5 行。正确结果是新建 8、+1、−1，1.5.1 的结果是新建 5、+0、−0。尚未修复。

2. **修改后的内容缺失时会算出大量删除行。** 如果一条 fs_write / fs_append 记录带有修改前的内容（`originalContent`），但修改后的内容（`modifiedContent`）缺失或不是文本，1.5.1 会把整个原文件算作删除，当天的"修改−行"会异常大，接近整个文件的行数。1.5.0 遇到这种记录会直接跳过。目前还没有在真实数据中见到这种记录。测试中如果发现某天的修改−行异常大，请反馈。
